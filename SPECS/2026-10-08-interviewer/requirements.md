# The Interviewer — requirements (Phase 3)

Feature spec for ROADMAP.md Phase 3: *"Sequential, stateful Q&A that
accumulates the dossier and picks an animal."* It defers to `SPECS/MISSION.md`,
`SPECS/TECH.md`, and `SPECS/ROADMAP.md` for anything not stated here.

## Context

Phase 2 left the repository in this state:

- `state.py` holds the single shared, versioned `StateDriver`
  (`SCHEMA_VERSION = 1`) with phases `AWAITING_PHOTO`, `INTERVIEWING`,
  `SCRIPTING`. The session carries the accepted photo's bytes; there is no
  dossier, no question bookkeeping, and no `CONVERTING` phase yet (TECH.md
  names it as part of the state machine).
- `bouncer.py` + `vision.py` established the stage pattern this phase reuses:
  an ADK `LlmAgent` on `gemini-3.1-flash-lite` with a Pydantic `output_schema`,
  raw structured output parsed at the edge into a typed model, `log_call`
  decorator logging, and a synchronous client driving async ADK sessions with
  `asyncio.run`.
- `bot.py` routes a photo through the Bouncer; the pass path parks the session
  in `INTERVIEWING`, stores the photo, and replies with the Phase 1 placeholder
  `"hey mate!"`. **Every other message** gets that same placeholder. There is
  no `/start` or `/restart` handling.
- `scripts/test` (pytest + ruff + mypy) is green; that greenness is the ground
  truth for this phase too.

The Interviewer is TECH.md's **orchestrator**: the stage that owns the
conversation loop, decides which phase runs next, and holds the dossier. This
is also the first stage whose behaviour spans many Telegram messages, so
correct resume-from-session is the core of the phase.

## User-approved intent

Decided with the user on 2026-10-08:

1. **3–4 questions**, generated by Gemini each interview (not a fixed script),
   investigative/playful/slightly eccentric in tone, adapting to the answers
   already given.
2. **One question per turn.** On a Bouncer pass the first question is sent as
   the reply (the placeholder reply disappears from the pass path). Each
   subsequent inbound text is recorded as the answer and answered with exactly
   **one** next question — the bot always waits for the response before
   continuing, never bundling questions or skipping ahead.
3. **After the final answer:** the responses are synthesised into a concise
   behavioural/personality profile (quirks, habits) plus a clear suggested
   animal. The user sees a short in-character reply **revealing the animal
   only**; the full profile stays internal.
4. **Handoff:** the completed profile and suggested animal are persisted in
   the session and the phase advances to the next pipeline stage
   (`CONVERTING`) — the Converter (Phase 4) reads them from there.
5. **Resume:** state is keyed by `chat_id`, so the interview continues
   correctly across separate Telegram messages and survives concurrent
   interviews in different chats.
6. **Reset:** mid-interview `/start` or `/restart` clears the dossier and
   restarts cleanly, in-process.

## Scope

### In scope

- The Interviewer agent (Google ADK, `gemini-3.1-flash-lite`) with **two typed
  output contracts**: the next question, and the final profile + animal.
- Question budget of **3–4**, enforced by code (floor and ceiling both hard),
  with the model choosing freely only inside those bounds.
- Session-state extension: a typed dossier sub-model (questions, answers,
  completed profile, suggested animal), a new `CONVERTING` phase, and the
  schema-version bump that cleanly invalidates stale in-memory sessions.
- Orchestrator duties: the Interviewer drives `INTERVIEWING → CONVERTING`
  through the single shared `StateDriver`; it never bypasses it.
- `bot.py` routing: `/start` and `/restart` resets, the interview turn loop,
  and the pass path handing over to the Interviewer.
- Idempotent interview start: a photo arriving while an interview is already
  in progress re-sends the pending question instead of clobbering the
  accumulated dossier.
- Tests: budget bounds, turn-taking, resume, reset, isolation, typed-contract
  failures, graceful degradation — offline by default, plus an opt-in live
  test against the real model.

### Out of scope (YAGNI)

Everything below is explicitly **not** built, configured, or left room for:

- The Converter, Scripter, or Narrator themselves (Phases 4–6). This phase
  only stores what they will read and advances the phase.
- Wrong-payload guards and broad API-timeout fallbacks — those are Phase 7.
  (The idempotent start above is not a guard: it is the Interviewer's correct
  own-behaviour so a stray photo cannot destroy the dossier.)
- Showing the full profile text to the user, previewing it, or any other
  reply-format knob.
- Webhooks, database/persistence, group-chat usage, multi-language support.
- A stored "budget" config field, question-count toggles, or extension points
  — the budget bounds are constants; progress is the recorded Q&A itself.

## Decisions

These are fixed for this feature; deviation requires updating the specs in
`SPECS/`.

1. **Model:** `gemini-3.1-flash-lite` via Google ADK, per the TECH.md stack
   table — same client pattern as `vision.py`. No other model is introduced.
2. **Typed contracts, never free text.** The model answers through two
   Pydantic schemas:
   - `NextQuestion { question: str, is_final: bool }` — the question to ask,
     plus whether the interview finishes once it is answered.
   - `InterviewProfile { profile: str, suggested_animal: str }` — the
     synthesised dossier summary and the animal for the next agent.

   Anything that fails these schemas is a **handled error**
   (`InterviewerError`), logged loudly, never interpreted downstream.
3. **Budget 3–4 is code-enforced.** The model may only mark a question final
   once at least 3 questions have been asked, and never past 4: the fourth
   question is always final regardless of model output, and no fifth question
   can be generated. The floor protects against a terse model, the ceiling
   against an over-curious one; both are unit-tested against hostile model
   output.
4. **Session schema v2.** `SCHEMA_VERSION` bumps to 2; the session gains a
   typed dossier (questions, answers, profile, suggested animal) and the phase
   enum gains `CONVERTING`. All reads and writes go through the one shared
   `StateDriver`; the Interviewer receives the driver by injection, no stage
   touches a raw session dict.
5. **Orchestration lives in the Interviewer.** It owns the turn loop and the
   `INTERVIEWING → CONVERTING` transition. `bot.py` stays a thin gateway: it
   routes by phase and delegates; it does not implement interview logic.
6. **Reveal policy:** the user is told the suggested animal in character; the
   profile string is internal (session state only) and is never sent as its
   own message.
7. **Start is idempotent:** calling start when an interview is already in
   progress returns the currently pending question unchanged — the dossier is
   never silently reset by a photo.
8. **Commands:** `/start` and `/restart` both purge the session via
   `StateDriver.reset` (which also drops the stored photo bytes) and reply
   with a short in-character invitation to send a fresh portrait. The
   `@BotName` suffix Telegram appends in groups is stripped before matching —
   though groups remain out of scope.
9. **Logging:** decorator-based via the existing `logutil.log_call`
   (entry/exit/duration/exception) — no log statements in business logic.
10. **Testing:** Red/Green TDD. The default suite stays fully offline (fake
    interview client); the live test runs only when `GEMINI_API_KEY` is set.
11. **Security non-negotiables** (MISSION.md): no cross-user leakage — two
    `chat_id`s never share a dossier, photo, or reveal; no hardcoded secrets.
12. **Constitution sync (user-approved):** `MISSION.md`, `ROADMAP.md`, and
    `README.md` are updated from "5–7 questions" to "3–4 questions" as part of
    this spec, so the contract and the code agree.

## Acceptance criteria (from ROADMAP.md Phase 3)

- 3–4 questions asked **one at a time**, each answer persisted to the session.
- On completion the dossier is summarised and a suggested animal is produced.
- The completed profile + suggested animal are persisted for, and handed to,
  the next pipeline stage.
- The Interviewer drives the state machine as orchestrator.
- Mid-interview `/start` or `/restart` clears the dossier and restarts
  cleanly.
- `scripts/test` runs green (pytest + ruff + mypy).

## Verification

- **Turn test:** a fake scripted interview walks photo → Q1 → answer → Q2 →
  answer → Q3 → (optional Q4) → completion, asserting exactly one question per
  turn and answers persisted at each step.
- **Budget tests:** hostile model output asking to finish at 2 questions or
  continue past 4 is overridden by the code-enforced bounds.
- **Handoff test:** after the final answer the session holds a non-empty
  profile and a non-empty suggested animal and the phase is `CONVERTING`; the
  user-facing reply contains the animal and not the profile.
- **Reset test:** mid-interview `/start` and `/restart` each leave the chat at
  `AWAITING_PHOTO` with no dossier, and the conversation can begin again.
- Both paths exercised with a stubbed interview client so `scripts/test` runs
  offline; a live opt-in check exists for the real `gemini-3.1-flash-lite`
  interview (details in `validation.md`).
